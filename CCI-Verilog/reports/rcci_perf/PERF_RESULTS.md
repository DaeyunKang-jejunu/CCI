## 측정 환경

- **TB.** ACE top 통합 TB(`tb_cci_ace_integration.sv`)의 `RCCI_PERF` 모드.
- **구성.**
  - B1-T{1,2,4,8,16}: 엔트리와 트래커 T개, DMA는 라인 요청을 최대 T개 outstanding으로 낸다.
  - R-E16-RW{w}-WE16-WW{w} (w = 1, 2, 4, 8, 16): 범위 context 16개, line tracker 16개, 창 w.
  - B1-T16과 R-E16-RW16에는 CPU 토큰 1개 예약 구성(`-RSV1`)을 추가했다.
- **공통 조건.** 토큰 T = 16, ACE manager context 4개, snoop service context S = 4, TB 메모리 outstanding Q = 16, 메모리 응답 지연 3 cycle, CPU 캐시 256라인(direct-mapped).
- **DMA 요청.** B1은 라인마다 ReadOnce / WriteLineUnique, rCCI는 4 KB(64라인)마다 ReadRange / WriteRange 하나.
- **CPU 부하.** 범위 전송 동안 ACE ReadShared를 40 cycle 간격으로 낸다.

> **메모리 모델의 제약.** TB의 `axi_memory_slave`는 읽기 burst를 하나씩 처리하므로 miss 읽기 상한은 라인당 약 8 cycle, 쓰기는 약 5 cycle이다. B1과 rCCI에 똑같이 적용된다. RTL 처리량은 "같은 메모리에서의 비교"로 해석한다.

## 주요 결과 (RTL)

### 1. 엔트리 점유와 DMA 요청 수

| 구성 (256라인) | 읽기 평균/최대 엔트리 | 쓰기 평균/최대 엔트리 | DMA 요청 수 |
|---|---|---|---|
| B1-T16 | 15.2 / 16 | 15.2 / 16 | 256 |
| B1-T4 | 3.7 / 4 | 3.8 / 4 | 256 |
| **rCCI E16·N_fly16** | **2.5 / 4** | **2.5 / 4** | **4** |

읽기 평균 엔트리: 8라인 B1-T16 4.67 / rCCI 0.99, 64라인 13.73 / 1.00. 256라인은 4 KB 범위 4개이므로 rCCI 엔트리가 최대 4개까지 찬다.

**E의 영향.** E = 4와 E = 16의 rCCI 74회 결과는 모든 항목이 같았다. 이 측정은 범위가 최대 4개만 동시에 존재하므로 E > 4는 쓰이지 않는다.

### 2. 처리량 (256라인, cycle/라인)

| T 또는 N_fly | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| B1 읽기 | 23.0 | 11.53 | 8.06 | 8.06 | 8.06 |
| rCCI 읽기 | **21.0** | **10.54** | 8.06 | 8.06 | 8.06 |
| B1 쓰기 | 23.0 | 11.52 | 5.81 | 5.07 | 5.07 |
| rCCI 쓰기 | **21.0** | **10.53** | **5.32** | 5.07 | 5.07 |

- 창이 충분하면(읽기 ≥4, 쓰기 ≥8) 두 방식 모두 메모리 상한에서 같다.
- 창이 작을 때 rCCI가 8~9% 빠르다.
- 첫 데이터 지연은 두 방식이 같다: 읽기 18 cycle, 쓰기 13 cycle.

**보완 13(R8)의 영향.** miss 라인을 4 beat 모두 트래커 버퍼에 받은 뒤 외부 R로 보내는 구조가 되어, B1과 rCCI 모두 읽기 첫 데이터가 14 → 18 cycle로 늘었다. 창이 1~2일 때 읽기는 라인당 약 2~4 cycle 느려졌다(B1 19.0 → 23.0, rCCI 17.0 → 21.0). 창 ≥4의 처리량은 거의 같다(8.04 → 8.06). 쓰기는 변화가 없다.

### 3. dirty 비율 (256라인, cycle/라인)

| dirty % | 0 | 25 | 50 | 100 |
|---|---|---|---|---|
| 읽기 (B1-T16 = rCCI-16) | 8.06 | 6.07 | 4.07 | 5.05 |
| 쓰기 (B1-T16 = rCCI-16) | 5.07 | 5.07 | 5.07 | 5.07 |

읽기 hit는 CD 데이터로 응답하므로 메모리 읽기를 우회한다. 쓰기(MakeInvalid)는 dirty 비율과 무관하다.

### 4. CPU 요청 지연 (256라인 DMA 중 ReadShared, 비충돌, cycle)

| 구성 | 읽기 DMA 중 평균/최대 | 쓰기 DMA 중 평균/최대 | CPU 토큰 대기 평균 (읽기 / 쓰기) |
|---|---|---|---|
| B1-T16 | 99 / 112 | 20 / 23 | 2.8 / 1.8 |
| B1-T4 | 27 / 27 | 18 / 18 | 0 / 0 |
| rCCI E16·N_fly16 | 118 / 128 | 18 / 20 | 0 / 0 |
| rCCI E16·N_fly4 | 32 / 32 | 18 / 18 | 0 / 0 |

- CPU 지연은 토큰이 아니라 동시 진행 라인 수에 따른 메모리 큐잉이 결정한다. 읽기 DMA 중 rCCI(N_fly 16)는 B1-T16보다 길다.
- 보완 13 이전과 비교하면 N_fly 4 구성의 읽기 중 지연이 B1-T4 35 → 27, rCCI 39 → 32로 줄었다.
- `CPU_RESERVED_TOKENS = 1`은 B1-T16의 평균 지연을 줄였고(읽기 99 → 93, 쓰기 20 → 18), rCCI에서는 변화가 없다(토큰 대기가 원래 0).
- 따라서 "CPU 지연 감소"를 RTL 결과로 주장할 근거는 이 환경에서 나오지 않는다.

## C++ 모델

### 64라인 RTL 대조 (`cpp_vs_rtl_64lines.csv`)

- 보정 파라미터: lm = 4, lc = 12(읽기·쓰기), lw = 1. 읽기 lc는 보완 13의 버퍼링 지연을 반영해 8에서 12로 바뀌었다.
- 오차: 읽기 평균 1.7%(최대 −8.6%), 쓰기 평균 9.5%(최대 −21.7%). 창 ≥4의 읽기는 0%.
- 모델은 작은 창의 지연을 과소평가하므로 MB 단위 결과는 창 ≥4 영역에서만 정량적으로 쓴다.

### MB 단위 sweep (`cpp_sweep_1MB.csv`, 576점)

- 조건: 스트림당 1 MB, 스트림 1/4개, T ∈ {4, 8, 16}, N_fly ∈ {4, 8, 16}, S ∈ {1, 2, 4, 8}, Q ∈ {4, 8, 16}(파이프라인 메모리)
- **토큰이 부족한 경우(4 스트림, T = 4, S = 4, Q = 16).**

  | | B1 | rCCI N_fly 4 | rCCI N_fly ≥8 |
  |---|---|---|---|
  | 읽기 처리량 (lines/cycle) | 0.190 | 0.190 | **0.250** |
  | 쓰기 처리량 (lines/cycle) | 0.222 | 0.222 | **0.250** |
  | 평균 토큰 사용 | 4.0 | 2.5 | 2.5 |

- **S의 영향(rCCI 1 스트림).** 처리량은 S = 1에서 0.077, S = 2에서 0.154, S ≥ 4에서 0.250으로 포화한다.

## 논문 5.2절에 대한 함의

- **확인된 주장.** 범위 하나가 엔트리 하나를 점유한다. DMA 요청 수가 256에서 4로 준다. 창이 같거나 작을 때 처리량이 같거나 더 좋다. 토큰이 부족한 다중 스트림에서 처리량이 높다(C++).
- **조정이 필요한 주장.** CPU 지연 감소는 이 RTL 환경에서 관측되지 않았다.

## 남은 범위

- TB 메모리가 직렬이므로 RTL 처리량의 절대값은 메모리 상한에 묶여 있다.
- 시험은 결정적이라 실행할 때마다 결과가 같다.
