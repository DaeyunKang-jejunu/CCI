# 하드웨어 비용 — 기존 방식 대비 제안 방식의 추가 비용 (논문 5.3절 자료)

실행일: 2026-11-10

이 측정의 목적은 **제안 방식을 하드웨어로 구현할 때 기존 방식 대비 비용이 얼마나 늘어나는가**를 보는 것이다.

## 실행 명령

```sh
python3 scripts/run_rcci_cost.py
python3 scripts/run_rcci_cost.py --from-run reports/runs/rcci_cost_<id>   # 리포트 재파싱만
```

## 비교 방법

| 항목 | 기존 방식 (B1) | 제안 방식 (rCCI) |
|---|---|---|
| 구성 | 라인 요청만 처리. 범위용 레지스터·카운터·구간 비교 없음 | **B1의 하드웨어를 모두 유지**(라인 CAM 포함)하고 범위 처리 하드웨어를 추가 |
| 용량 | 엔트리·트래커·동시 진행 라인 = 16 (또는 8) | **같은 값** (E = T = N_fly = 16 또는 8) |

제안 방식에 추가된 하드웨어: 범위 context의 카운터(`lines`, `issue_idx` 등), 구간 레지스터(`lo/hi` 페이지 내 라인 오프셋 7비트 × 2), 엔트리별 구간 비교(페이지 일치 + 오프셋 비교), 범위 분해·발행 제어.

## 구현 환경

- Vivado 2024.1, `xczu7ev-ffvc1156-2-e`(Zynq UltraScale+), out-of-context synthesis, 클럭 제약 없음(unconstrained). 모든 구성에 같은 흐름과 옵션을 썼다.
- synthesis-only이다. 배치·배선을 하지 않았으므로 timing은 주장하지 않는다.
- 공통 조건: 128비트 데이터 버스, 공통 토큰 16, ACE manager context 4개, snoop service context 4개.

## 2. 증가분의 위치 (16 엔트리, LUT / FF)

| 블록 | B1-T16 | rCCI | 증가 |
|---|---|---|---|
| write range adapter (Range Controller, 구간 비교) | 1,837 / 1,306 | 6,062 / 1,982 | **+4,225 / +676** |
| read ingress (Range Controller, 구간 비교, line tracker) | 27,856 / 9,965 | 30,756 / 10,600 | **+2,900 / +635** |
| write line ingress (라인 CAM) | 5,970 / 1,435 | 6,051 / 1,435 | +81 / 0 |
| read 서비스 응답 adapter | 4,419 / 540 | 2,932 / 532 | −1,487 / −8 |
| admission pool | 1,490 / 52 | 932 / 52 | −558 / 0 |
| snoop service | 4,633 / 2,627 | 4,598 / 2,623 | −35 / −4 |
| ACE manager | 10,993 / 3,641 | 10,903 / 3,641 | −90 / 0 |

- 증가분은 범위 처리를 담당하는 두 블록에 있다(합계 +7,125 / +1,311).
- 응답 adapter와 admission pool은 두 구성의 RTL이 같다. 차이는 제약 없는 합성의 결과 편차이며, 이 때문에 top 증가분(+5,316)이 두 블록의 합보다 작다. 블록별 LUT는 이 정도의 편차를 감안해서 읽는다.

## 3. 해저드 비교기 단독 (`synth/cost_cam_wrappers.sv`)

입출력 레지스터 경계, valid gating, 포트별 OR 축약 조건을 같게 두었다(포트 5개).

| 구성 | 엔트리 | LUT | FF |
|---|---|---|---|
| line CAM (B1) | 16 | 3,568 | 1,442 |
| interval CAM (rCCI) | 16 | 2,243 | 1,390 |
| line CAM (B1) | 8 | 1,785 | 962 |
| interval CAM (rCCI) | 8 | 1,119 | 854 |

구간 비교는 페이지 일치 검사(52비트)와 7비트 오프셋 비교로 구현한다. 범위는 항상 4 KB 페이지 안에 있기 때문이다. 제안 방식에서는 이 비교기가 라인 CAM에 **추가**된다.

## 4. 해석상 주의

- **이번 구성은 라인 CAM과 구간 비교를 모두 둔다.** 발행된 범위 라인은 line tracker에도 있으므로 두 비교의 결과는 같다(시뮬레이션 assertion `HAZARD_INTERVAL_EQUIV`로 확인). 따라서 위 증가분은 "기존 하드웨어를 하나도 줄이지 않고 범위 하드웨어를 더한" 경우의 값이다.
- `lo/hi`를 59비트 전체 주소로 저장했던 구현의 값(+31.7% / +21.6%)은 `COST_ANALYSIS.md`의 분석에 따라 폐기했다.
- 기존 측정(엔트리 4개로 줄인 rCCI를 B1-T16과 비교한 LUT −32.6%)은 용량이 다르고, 기존 하드웨어를 제거한 구성이어서 **제안 방식의 비용으로 쓸 수 없다.** 이전 값은 사용하지 않는다.
- 결과 파일: `cost_top.csv`, `cost_modules.csv`, `cost_cam.csv`, `*_utilization.rpt`, `*_hier.rpt`, `summary.json`, `reports/hardware_cost.csv`.
