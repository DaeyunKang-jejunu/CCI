# 0. v9 변경 요약

v8에 대한 피드백은 기술적으로 합당하며, **conventional tracker의 할당 순서를 명시하지 않으면 실제 deadlock 가능성이 있으므로 필수 수정사항으로 반영한다.**

v9에서 conventional tracker allocation 정책을 다음과 같이 확정한다.

```text
1. M1 AW는 Common Ingress Queue에 acceptance order대로 저장
2. P에서는 ingress push 시 PATH를 즉시 분류
3. PATH=RANGE이면 같은 acceptance event에서 해당 line을 wr_issued_mask에 예약
4. PATH=CONVENTIONAL entry는 ingress age 순서대로 tracker를 할당
5. tracker allocation은 queue head만 대상으로 하지 않음
6. 단, 더 오래된 unallocated CONVENTIONAL entry를 건너뛰어 younger CONVENTIONAL entry에 tracker를 줄 수 없음
7. tracker가 할당된 여러 conventional entry는 AC를 파이프라인하여 multiple outstanding snoop을 만들 수 있음
8. downstream AW/W 발행은 계속 Common Ingress Queue head에서만 수행
```

이 정책은 두 목표를 동시에 만족한다.

- **Multiple conventional AC outstanding 허용:** head가 아닌 older queued entry도 tracker를 미리 할당받아 AC를 발행할 수 있다.
- **Tracker-depth < ingress-depth에서 deadlock 방지:** younger entry가 tracker를 모두 선점하여 오래된 head-side entry가 영원히 tracker를 받지 못하는 상황을 금지한다.

또한 다음 권장사항도 반영한다.

- P의 PATH classification은 **M1 AW ingress push handshake와 같은 acceptance event**에서 확정한다.
- PATH=RANGE이면 같은 event에서 `wr_issued_mask[idx]`를 set하여 해당 line을 range fast path에 예약한다.
- 이 문서에서 `wr_issued_mask`의 "issued"는 **downstream AW handshake가 아니라 range path에 acceptance/reservation된 상태**를 의미한다.
- downstream `wr_q`의 `ingress_idx`는 B1/P 공통 metadata로 정의한다.
- `is_range`는 `ingress_queue[ingress_idx].PATH`에서 복원하므로 P만의 `wr_q` field로 저장하지 않는다.
- 따라서 downstream B association queue의 proposal-specific metadata 증가는 원칙적으로 0이다.
- 문서 내 오래된 버전 표기는 제거하거나 v9 기준으로 통일한다.

# 2. 최종 구조 결정

## 2.1 Proposed는 additive 구조

최종 proposed 시스템:

```text
P = B1 Conventional Coherent Baseline
    + Range Coherence Fast Path
```

### 일반 M1 write

```text
range에 속하지 않는 write
또는
이미 range fast path로 한 번 사용된 target line의 후속 write

→ B1 conventional per-line coherence path
```

### 첫 번째 registered memcpy-range write

```text
active range의 target line
& 아직 wr_issued_mask가 set되지 않은 line

→ range fast path
```

따라서 B1과 P의 외부 기능 범위는 동일하다.

최종 proposal-specific hardware cost:

```text
P - B1
```

---

## 2.2 Common M1 Ingress Queue는 B1/P 공통

B1과 P 모두 동일한 M1 AW ingress/order queue를 사용한다.

### 공통 queue의 역할

```text
- upstream M1 AW 수용
- AW acceptance order 보존
- AWID/AWADDR/AWLEN metadata 보존
- WDATA ordering 기준 제공
- downstream AW issue order 보존
```

### B1

모든 ingress entry는:

```text
PATH = CONVENTIONAL
```

로 처리한다.

### P

각 ingress entry는 classify 후:

```text
PATH = CONVENTIONAL
또는
PATH = RANGE
```

로 처리한다.

### 중요한 cost 원칙

queue 자체의 storage:

```text
AWID
AWADDR
AWLEN
VALID/state
```

는 B1/P 공통이다.

P에만 추가되는 field는 원칙적으로:

```text
PATH : 1 bit / entry
```

정도이다.

`LINE_IDX`는:

```text
AWADDR[11:6]
```

에서 다시 계산할 수 있으므로 별도 저장하지 않는다.

따라서 queue depth가 16이라면 proposal-specific sequential state 증가는 대략:

```text
PATH 1 bit × 16 entries = 16 bits
```

수준이다.

> 실제 FF primitive 수는 Vivado 최적화와 packing에 따라 달라질 수 있다.

---

## 2.3 Conventional tracker는 ingress queue와 분리

Common ingress queue와 conventional line tracker는 서로 다른 역할이다.

### Ingress queue

```text
"어떤 AW가 어떤 순서로 들어왔는가?"
```

를 관리한다.

### Conventional line tracker

```text
"어떤 cache line이 conventional coherence transaction으로 in-flight인가?"
```

를 관리한다.

따라서 B1도 처음부터:

```text
Common M1 Ingress Queue
+ Conventional Line Tracker
```

구조를 사용한다.

P에서 range write는:

```text
Ingress Queue entry는 사용
Conventional Line Tracker는 사용하지 않음
```

으로 구현한다.

이 구조가 range 방식의 runtime tracker-pressure 감소를 실제로 표현한다.

---

## 2.4 Range INVALIDATING 동안 AC source 독점

P에는 두 종류의 coherence AC source가 존재한다.

```text
1. Conventional per-line MakeInvalid
2. Range MakeInvalid
```

CR에는 source tag가 없으므로 두 source를 섞어 발행하면 range CR count가 오염될 수 있다.

따라서:

```text
Range state == INVALIDATING:
    Range AC만 발행
    Conventional AC 발행 금지
```

로 한다.

range의 모든 required CR 완료 후:

```text
state = TRACKING
```

으로 전환되면 conventional AC 발행을 다시 허용한다.

---

## 2.5 Conventional B1에서는 AC-order FIFO 사용

여러 conventional tracker entry의 AC가 outstanding일 수 있으므로 B1은:

```text
conv_ac_order_fifo
```

를 사용한다.

AC handshake 시 tracker index를 push하고 CR handshake 시 pop하여 해당 tracker entry의 `SNOOP_DONE`을 갱신한다.

이 FIFO는 B1/P 공통 conventional infrastructure이므로:

```text
P - B1
```

proposal-specific delta에는 직접 포함되지 않는다.

# 4. 신규 AXI 모델을 사용하는 이유

신규 AXI 모델은 full ACE/CCI는 아니지만 기존 `full_cci`보다 다음 transaction 구조를 명시적으로 제공한다.

- 2 master → 1 slave arbitration
- AW/W/B
- AR/R
- AXI ID
- outstanding queue
- response routing
- WDATA burst
- backpressure
- multiple outstanding

기본:

```text
DATA_WIDTH = 128 bit
BURST_BEATS = 4
```

이면:

```text
16 B/beat × 4 beats = 64 B
```

로 한 cache line과 일치한다.

이를 기반으로 다음을 재구성한다.

1. AW→W→B association
2. actual B completion
3. common ingress ordering
4. multiple conventional tracker occupancy
5. conventional AC→CR tracker association
6. M0 AR/AW hazard
7. range/conventional write 공존

---

# 5. 비교 구성

## 5.1 B0 — Pure AXI Reference

```text
corrected AXI 2-to-1 shell
+ AW/W/B
+ AR/R
```

B0는 AXI structural reference이며 conventional CCI baseline은 아니다.

---

## 5.2 B1 — Conventional Per-Line Coherent Baseline

```text
B0
+ Common M1 Ingress Queue
+ common AC/CR endpoint
+ 16-entry per-line tracker
+ conventional AC scheduler
+ conventional AC-order FIFO
+ line MakeInvalid
+ CR→tracker association
+ actual B completion
+ M0 AR/AW hazard CAM
```

### B1 write flow

```text
M1 AW accepted into Common Ingress Queue
      ↓
PATH = CONVENTIONAL
      ↓
Ordered Tracker Allocation Engine
      ↓
oldest unallocated CONVENTIONAL entry부터 tracker 할당
(head일 필요는 없음)
      ↓
할당된 entry는 AC issue 가능
      ↓
AC handshake
      ↓
tracker index → conv_ac_order_fifo push
      ↓
CR handshake
      ↓
FIFO pop
      ↓
matching tracker SNOOP_DONE
      ↓
downstream issue는 오직 Ingress Queue head에서만 허용
      ↓
head의 coherence condition이 완료되면 AW/W downstream
      ↓
actual B
      ↓
tracker release
      ↓
ingress entry retire
```

따라서 **tracker allocation/AC 진행은 head보다 앞서 파이프라인될 수 있지만, downstream AW/W 순서는 ingress head가 강제한다.**

---

## 5.3 P — Additive Range-Coherent Design

```text
P =
B1
+ PATH field/classifier
+ 251-bit logical range context
+ range early invalidation
+ range write_release
+ dual range hazard checker
+ range admission/drain control
+ range B-completion metadata
```

### Conventional entry

```text
Ingress Queue 사용
+
Conventional Tracker 사용
```

### Range entry

```text
Ingress Queue 사용
+
Conventional Tracker bypass
+
Range Context 사용
```

즉 P에서 range write는 **공통 ingress/order infrastructure는 그대로 사용하면서 conventional tracker slot만 소비하지 않는다.**

초기:


로 conventional tracker depth 및 AXI outstanding 설정과 맞춘다.

---

## 6.2 B1 entry

최소:

```text
VALID
AWID
AWADDR[63:0]
AWLEN
STATE
```

를 가진다.

`STATE`는 구현에 따라 다음 의미를 분리해서 갖도록 한다.


- PATH classification: ingress push 시 확정
- Conventional tracker allocation: ingress age 순서대로 별도 진행


# 7. B1 Conventional Tracker

## 7.1 Depth

```text
LINE_TRACKER_ENTRIES = 16
```

---

## 7.2 최소 entry

개념적으로:

```text
VALID
LINE_ADDR = AWADDR[63:6]
STATE
INGRESS_IDX
AC_ISSUED
SNOOP_DONE
DOWNSTREAM_ISSUED
```

AXI AW metadata 자체는 Common Ingress Queue에 있으므로 tracker에 다시 전체 `AWADDR/AWID/AWLEN`을 중복 저장할 필요가 없다.

### 권장

tracker는:

```text
INGRESS_IDX
LINE_ADDR 또는 필요한 address tag
coherence state
```

위주로 최소화한다.

---

## 7.3 Conventional tracker allocation

B1에서는 모든 M1 coherent write가 conventional tracker를 사용한다.

P에서는:

```text
PATH == CONVENTIONAL
```

인 ingress entry만 tracker를 할당한다.

```text
PATH == RANGE
```

인 entry는 tracker slot을 소비하지 않는다.

---

## 7.4 Ordered Conventional Tracker Allocation

Conventional tracker는 **ingress queue의 head에만 할당하는 구조가 아니다.**

여러 queued conventional write가 snoop을 미리 진행할 수 있도록 head 뒤의 entry도 tracker를 할당받을 수 있다.

다만 allocation은 반드시 **ingress age order**를 따른다.

### 규칙

```text
oldest_unallocated_conventional
    = ingress queue에서 가장 오래된
      PATH=CONVENTIONAL &&
      tracker 미할당 entry
```

free tracker가 있으면 오직 이 entry에 tracker를 할당한다.

```text
if oldest_unallocated_conventional exists
   && free_tracker exists:
       allocate tracker
       tracker.INGRESS_IDX = entry index
       entry.TRACKER_ALLOCATED = 1
```

### 금지

```text
older CONVENTIONAL entry가 tracker를 기다리는 상태에서
younger CONVENTIONAL entry가 먼저 tracker를 할당받는 것
```

을 금지한다.

RANGE entry는 conventional tracker가 필요 없으므로 allocation scan에서 건너뛴다.

### 왜 필요한가

예를 들어:

```text
M1_INGRESS_DEPTH     = 16
LINE_TRACKER_ENTRIES = 4
```

에서 younger entry가 임의 순서로 tracker 4개를 모두 선점할 수 있다면, 더 오래된 head-side conventional entry가 tracker를 얻지 못할 수 있다.

그 경우:

```text
older entry:
tracker가 없어서 issue 불가

younger entry:
tracker는 있지만 strict HOL 때문에 issue 불가
```

가 되어 deadlock이 가능하다.

Ordered allocation을 사용하면 tracker는 항상 가장 오래된 conventional entries부터 채워지므로 적어도 oldest allocated entry가 head에 도달해 progress하고 tracker를 반환할 수 있다.

### Tracker-full stall 정의

sensitivity 실험에서:

```text
tracker_full_stall_cycle
```

은 다음 조건의 cycle로 정의한다.

```text
oldest_unallocated_conventional exists
&& no_free_tracker
```

즉 **순서상 다음 conventional entry가 tracker 부족 때문에 allocation을 기다린 cycle**을 센다.

---

## 7.5 Conventional AC scheduler

active tracker 중:

```text
VALID
& !AC_ISSUED
```

인 entry를 선택한다.

초기 prototype에서는 deterministic하게 **ingress age가 가장 오래된 allocated conventional entry**를 우선 선택한다.

tracker allocation과 AC response는 downstream head issue와 독립적으로 선행할 수 있으므로, CR latency가 존재하면 여러 conventional AC가 동시에 outstanding 상태가 될 수 있다.

ACVALID이 stall되면 selected tracker/payload는 handshake까지 유지한다.

---

## 7.6 Conventional AC-order FIFO

FIFO payload:

```text
TRACKER_IDX[3:0]
```

AC handshake:

```text
push(tracker_idx)
tracker[tracker_idx].AC_ISSUED <= 1
```

CR handshake:

```text
tracker_idx = pop()
tracker[tracker_idx].SNOOP_DONE <= 1
```

FIFO full이면 신규 conventional AC를 발행하지 않는다.

### 기본 depth에서의 도달 가능성

기본:

```text
LINE_TRACKER_ENTRIES = 16
CONV_AC_FIFO_DEPTH   = 16
```

이고 tracker entry당 conventional AC를 최대 한 번 outstanding으로 만드는 현재 구조에서는 FIFO occupancy의 최대값도 16이다.

FIFO가 16개 모두 차 있는 순간에는 16개 tracker가 이미 AC를 발행한 상태이므로, 추가 AC를 발행할 새로운 tracker entry가 남아 있지 않다. 따라서 기본 configuration에서는 `"FIFO full 때문에 otherwise-eligible AC가 추가로 stall되는 상황"`은 사실상 발생하지 않는다.

`fifo_full` gating은 robustness를 위해 유지하고, 해당 backpressure path는 별도의 reduced-depth stress test에서 검증한다.

예:

```text
LINE_TRACKER_ENTRIES = 16
CONV_AC_FIFO_DEPTH   = 4
```

또는:

```text
CONV_AC_FIFO_DEPTH   = 8
```

---

## 7.7 M0 hazard CAM

### Read

```text
M0_ARADDR[63:6]
vs
all active tracker LINE_ADDR
```

### Write

```text
M0_AWADDR[63:6]
vs
all active tracker LINE_ADDR
```

하나라도 match하면 해당 request를 admission하지 않는다.

# 8. B1/P AW/W/B Ordering

## 8.1 AW acceptance

M1 AW는 먼저 Common Ingress Queue에 들어간다.

B1/P 모두 동일하다.

---

## 8.2 WDATA

AXI4 W에는 WID가 없으므로 write-data order를 유지한다.

초기 정책:

1. ingress queue acceptance order 유지
2. downstream AW issue도 동일 order 유지
3. head entry가 issue 가능해질 때까지 WREADY backpressure
4. full WDATA buffer는 두지 않음

---

## 8.3 B lifetime

Conventional tracker는:

```text
allocate
→ AC
→ CR
→ AW/W
→ B
→ free
```

까지 유지한다.

Range write의 progress는 range context의 `wr_issued_mask/done_mask`가 담당한다.

Ingress entry는 해당 transaction의 downstream/B lifecycle에 맞춰 retire한다.

# 9. Range Context — 251-bit logical state

`wr_issued_mask`는 `cci_range_rim_tracker` 내부 context state로 유지한다.

## 9.1 Field

```text
VALID            1
STATE            2
BASE_PAGE_ADDR   52
LINE_MASK        64
WR_ISSUED_MASK   64
DONE_MASK        64
SOURCE_ID         4
-------------------
Total           251 bits
```

---

## 9.2 Allocation

새 context 할당:

```text
line_mask       <= generated_line_mask
wr_issued_mask  <= 0
done_mask       <= 0
```

---

## 9.3 Range classification

P ingress entry의 AWADDR를 기준으로:

```text
page_match =
AWADDR[63:12] == active_range_page

idx =
AWADDR[11:6]

is_range_write =
range_active
& page_match
& line_mask[idx]
& ~wr_issued_mask[idx]
```

---

## 9.4 PATH classification 및 range reservation 시점

PATH classification은 **M1 AW가 Common Ingress Queue에 실제 push되는 handshake와 같은 acceptance event**에서 수행한다.

즉:

```text
m1_aw_push =
M1_AWVALID && M1_AWREADY
```

가 발생하는 cycle에 accepted `AWADDR`와 현재 active range state를 이용해:

```text
if is_range_write:
    entry.PATH = RANGE
else:
    entry.PATH = CONVENTIONAL
```

을 확정한다.

PATH는 해당 ingress entry가 retire할 때까지 변경하지 않는다.

### RANGE reservation

같은 push event에서 PATH=RANGE로 결정되면:

```text
wr_issued_mask[idx] <= 1
```

도 원자적으로 수행한다.

따라서:

```text
M1 AW push
→ PATH classification
→ RANGE이면 wr_issued_mask reservation
```

이 하나의 논리적 acceptance event이다.

이는 같은 target line의 다음 write가 뒤 cycle에 들어왔을 때 이미:

```text
wr_issued_mask[idx] == 1
```

을 보게 하여 conventional fallback으로 분류되도록 한다.

### 용어 주의

본 prototype에서 `wr_issued_mask`의 "issued"는:

> **해당 line이 range fast path transaction으로 ingress에서 accepted/reserved되었다**

는 의미이다.

반드시:

> downstream slave로 AW handshake가 이미 완료되었다

는 의미는 아니다.

필요하면 최종 RTL에서 혼동을 줄이기 위해 `wr_reserved_mask`로 rename하는 것도 가능하지만, 본 문서에서는 기존 용어와의 연속성을 위해 `wr_issued_mask`를 유지한다.

---

## 9.6 Completion

actual B handshake:

```text
done_mask[idx] <= 1
```

## 9.7 Invariant

```text
done_mask ⊆ wr_issued_mask ⊆ line_mask
```

# 10. 동일 Target Line 중복 Write

같은 target line에 후속 write가 들어오면:

```text
wr_issued_mask[idx] == 1
```

이므로:

```text
PATH = CONVENTIONAL
```

로 분류한다.

첫 range write B 완료 후 range hazard가 풀리더라도 후속 write는 conventional tracker가 hazard lifetime을 담당한다.

# 11. Range Operation 정상 완료 전제

현재 prototype은 다음을 전제로 한다.

> DMA가 range setup에서 등록한 모든 target line을 정상 overwrite하고 각 line의 range write가 actual B completion까지 도달한다.

정상 종료:

```text
wr_issued_mask == line_mask
done_mask      == line_mask
```

그리고:

```text
range_outstanding =
wr_issued_mask & ~done_mask
```

가 0이어야 한다.

target 일부가 쓰이지 않으면 context는 종료되지 않는다.

abort/cancel/recovery는 P2 범위이다.

Simulation에는:

```text
RANGE_MAX_ACTIVE_CYCLES
```

watchdog를 둔다.

# 12. Common Ingress HOL 정책

B1/P 모두 **동일 공통 ingress queue**를 사용하며 초기 구현은 reorder하지 않는다.

예:

```text
Head: RANGE, write_release=0
Next: CONVENTIONAL, snoop_done=1
```

이어도:

```text
Next entry는 head를 추월하지 않음
```

따라서 conventional write도 HOL wait한다.

이 동작은 P만의 queue cost가 아니라 B1/P 공통 ordering policy이다.

# 17. Actual B Completion Metadata

downstream AXI write transaction queue(`wr_q`)에는 B response를 Common Ingress Queue의 transaction과 다시 연결하기 위한:

```text
INGRESS_IDX
```

를 저장한다.

초기:

```text
M1_INGRESS_DEPTH = 16
```

이면:

```text
INGRESS_IDX = 4 bits
```

이다.

## 17.1 `INGRESS_IDX`의 비용 귀속

`INGRESS_IDX`는 P만을 위한 metadata가 아니다.

B1도 actual B가 도착했을 때:

- 어느 ingress entry를 retire할지
- 어느 conventional tracker lifecycle을 종료할지

식별해야 하므로 동일한 `INGRESS_IDX`를 사용한다.

따라서:

> **downstream `wr_q`의 `INGRESS_IDX` storage는 B1/P 공통 비용이다.**

P-B1 proposal-specific delta에 포함하지 않는다.

## 17.2 PATH/is_range 저장 여부

P에서 별도의:

```text
is_range
```

bit를 `wr_q`에 저장하지 않는다.

B handshake 시:

```text
ingress_idx = wr_q_head.INGRESS_IDX
path        = ingress_queue[ingress_idx].PATH
```

로 복원한다.

### Range B

```text
if path == RANGE:
    idx = ingress_queue[ingress_idx].AWADDR[11:6]
    range_done_valid = 1
    range_done_idx   = idx
```

### Conventional B

```text
if path == CONVENTIONAL:
    matching conventional tracker release
```

Ingress entry는 B response가 처리될 때까지 retire하지 않으므로 B 시점에도 `PATH`와 `AWADDR`가 유효해야 한다.

## 17.3 Cost 의미

이 구조에서는 downstream `wr_q` 관점에서:

```text
B1 common metadata:
    INGRESS_IDX

P-only additional wr_q metadata:
    0 bit
```

이다.

P의 proposal-specific state는 Common Ingress Queue의 `PATH` bit와 Range Context/control logic에 귀속된다.

## T3 — Ordered B1 tracker allocation

tracker allocation이 **head-only가 아니라 ingress age 순서**로 진행되는지 확인한다.

예:

```text
Ingress order:
C0, C1, C2, C3, C4, C5

LINE_TRACKER_ENTRIES = 4
```

기대:

```text
처음 tracker 할당:
C0, C1, C2, C3

C4, C5:
tracker free까지 대기
```

C1~C3은 아직 queue head가 아니어도 tracker를 할당받고 AC를 미리 발행할 수 있다.

반드시:

```text
C4가 C0~C3 중 더 오래된 unallocated conventional entry를 건너뛰어
먼저 tracker를 받는 상황
```

이 없어야 한다.

tracker 하나가 B completion으로 free되면 순서상 다음 oldest unallocated conventional entry가 할당받는다.

## T4 — P range tracker bypass

```text
conventional tracker allocation = 0
```

인지 확인.

## T5 — B1 multiple AC association

Ordered allocation으로 여러 conventional ingress entry가 tracker를 미리 확보한 상태에서 AC를 파이프라인한다.

예:

```text
allocated trackers:
tracker 3 → ingress C0
tracker 5 → ingress C1
tracker 9 → ingress C2
```

연속 AC handshake 후 FIFO:

```text
[3,5,9]
```

CR이:

```text
CR1 → tracker 3
CR2 → tracker 5
CR3 → tracker 9
```

로 정확히 배분되는지 확인한다.

즉 **downstream issue는 head-only여도 AC는 여러 allocated conventional entry에 대해 outstanding일 수 있어야 한다.**

## T6 — Conventional AC FIFO full (reduced-depth stress)

기본 16-tracker / 16-FIFO configuration에서는 추가 AC backpressure 상황이 실질적으로 도달하기 어렵다.

따라서 이 테스트는 별도 parameter configuration에서 수행한다.

예:

```text
LINE_TRACKER_ENTRIES = 16
CONV_AC_FIFO_DEPTH   = 4
```

테스트:

```text
FIFO가 full
→ 아직 AC를 발행하지 않은 tracker 존재
→ 신규 conventional AC handshake 금지
→ CR로 FIFO slot이 비면 AC issue 재개
```

기본 configuration에서는 대신:

```text
FIFO overflow 없음
FIFO count <= LINE_TRACKER_ENTRIES
```

을 확인한다.

## T14 — Tracker occupancy comparison (기본 16/16)

동일 memcpy workload에서:

### B1

여러 ingress entry가 각각 conventional tracker를 점유.

### P

동일 ingress depth를 사용하지만 RANGE entry는 conventional tracker를 점유하지 않음.

이 테스트는 static area가 아니라 **runtime tracker occupancy 차이**를 확인한다.

### 해석 제한

기본:

```text
M1_INGRESS_DEPTH     = 16
LINE_TRACKER_ENTRIES = 16
```

에서는 ingress queue와 tracker capacity가 동일하므로 conventional tracker capacity가 ingress보다 먼저 병목이 되지 않는다.

따라서 이 설정에서:

```text
P tracker occupancy < B1 tracker occupancy
```

가 관찰되더라도, **occupancy 감소 자체를 throughput/latency 향상으로 해석하지 않는다.**

---

## T14B — Tracker-depth sensitivity

보조 실험:

```text
M1_INGRESS_DEPTH = 16

LINE_TRACKER_ENTRIES =
4
8
16
```

각 point에서 B1/P는 동일 tracker depth를 사용한다.

측정:

```text
peak conventional tracker occupancy
tracker-full stall cycles
M1 ingress stall cycles
copy completion cycles
accepted writes/cycle
```

여기서:

```text
tracker-full stall cycle
=
oldest unallocated CONVENTIONAL entry가 존재하지만
free conventional tracker가 없어 allocation이 진행되지 못한 cycle
```

로 정의한다.

목적:

- tracker depth가 ingress depth보다 작은 상황에서 B1의 tracker pressure 확인
- P의 range write tracker bypass가 pressure를 줄이는지 확인
- tracker count와 memcpy 성능 사이의 design trade-off 분석

주의:

> 이 실험은 “P에서는 conventional tracker를 무조건 줄여도 된다”는 일반적 결론을 위한 것이 아니다. tracker 감소는 normal/non-range coherent traffic의 concurrency를 낮출 수 있으므로, memcpy-dominant workload에서의 sensitivity 결과로 한정한다.

B1에는 다음이 포함된다.

- **Common M1 Ingress Queue**
- Common Ingress Queue와 downstream `wr_q`를 연결하는 **INGRESS_IDX metadata**
- 16-entry conventional line tracker
- ordered conventional tracker allocation engine
- dual hazard CAM
- conventional AC scheduler
- conventional AC-order FIFO
- actual B lifetime control
- common AC/CR endpoint

P에서도 그대로 유지한다.

따라서 이 비용은:

```text
P - B1
```

에 다시 포함되지 않는다.

---

## 22.3 P-B1 추가 비용

P에서 B1 대비 새로 추가되는 것은:

- Ingress Queue의 **PATH field**
  - 약 1 bit × depth 16
- range request decoder
- 251-bit logical Range Context
- range AC generation/progress
- range membership/classifier
- range/conventional selector
- dual range hazard checker
- range admission/drain state
- range-specific B/completion association logic
  - 단, downstream `wr_q`에 P-only `is_range`/`line_idx` field는 추가하지 않음
- AC source phase control

### 중요한 제외 항목

다음은 P만의 비용으로 계산하지 않는다.

```text
AWID storage
AWADDR storage
AWLEN storage
common ingress depth
common ingress ordering state
```

이들은 B1/P 공통이다.

또한 downstream `wr_q`의:

```text
INGRESS_IDX
```

도 B1/P 공통이다.

P에서는:

```text
is_range = ingress_queue[INGRESS_IDX].PATH
line_idx = ingress_queue[INGRESS_IDX].AWADDR[11:6]
```

로 복원하므로 `wr_q`에 proposal-specific metadata bit를 추가하지 않는다.

---

## 22.4 왜 이 구조가 필요한가

만약 B1에서 AW metadata를 tracker 안에 합쳐 두고 P에서만 별도 ingress queue를 추가하면, P-B1에:

```text
16 × (AWADDR 64 + AWID + AWLEN + state...)
```

수준의 대규모 FF가 추가될 수 있다.

이는 range mechanism 자체 비용이 아니라 **microarchitecture baseline 불일치 비용**이다.

따라서 v8은 이를 제거하고 B1/P 모두 동일 ingress architecture를 사용한다.

---

## 22.5 Runtime tracker-pressure 의미와 기본 설정의 한계

v8 기본 구조:

```text
M1_INGRESS_DEPTH     = 16
LINE_TRACKER_ENTRIES = 16
```

에서 동일 memcpy workload를 비교하면:

### B1

```text
Ingress Queue:
최대 16 entries

Conventional Tracker:
최대 16 line entries
```

### P

```text
Ingress Queue:
동일 최대 16 entries

Conventional Tracker:
range write에 대해서는 사용하지 않음

Range Context:
1 page context 사용
```

따라서:

> **Ingress capacity는 동일한 상태에서 conventional coherence tracker occupancy가 감소한다.**

이는 제안 방식의 명확한 runtime **resource-usage effect**이다.

그러나 기본 16/16 설정에서는 tracker capacity가 ingress capacity보다 작지 않으므로, tracker occupancy 감소만으로 추가 request acceptance capacity가 생기지는 않는다.

따라서 기본 설정의 결과는:

```text
tracker occupancy 감소
```

를 보여주는 것으로 해석하고, 이를 단독으로:

```text
성능 향상
처리량 향상
latency 감소
```

의 근거로 사용하지 않는다.

전체 latency가 달라진다면 snoop/range sequencing 등 다른 원인과 분리해서 해석한다.

---

## 22.6 Tracker-depth sensitivity 실험

tracker pressure가 실제 backpressure로 이어지는 조건을 보기 위해 메인 area 실험과 별도로 다음 sweep을 수행할 수 있다.

```text
M1_INGRESS_DEPTH = 16

LINE_TRACKER_ENTRIES ∈ {4, 8, 16}
```

각 tracker-depth에서 B1/P는 동일 depth를 사용한다.

### 측정 항목

```text
Peak Conventional Tracker Occupancy
Tracker-full Stall Cycles
M1 Ingress Stall Cycles
Memcpy Completion Cycles
Accepted Writes/Cycle
```

### 예상되는 구조적 차이

B1:

```text
모든 memcpy destination write
→ conventional tracker 필요
```

P:

```text
registered range write
→ conventional tracker bypass
```

따라서 tracker depth가 ingress depth보다 작은 조건에서 B1은 tracker-full backpressure를 받을 수 있고, P는 memcpy traffic에 대해서 그 pressure를 줄일 수 있다.

### 논문 해석

이 결과가 확인되면 다음 수준으로 표현한다.

> **Range-based handling reduces the sensitivity of memcpy traffic to the number of conventional per-line tracker entries.**

다만:

- normal/non-range traffic에서는 P도 conventional tracker를 사용하고,
- tracker 수를 줄이면 그러한 traffic의 concurrency가 낮아질 수 있으므로,

이를 일반적인 `"tracker를 줄여도 성능 손실이 없다"`는 주장으로 확대하지 않는다.

이 sensitivity sweep은 **메인 P-B1 static hardware-cost 비교와 별도의 보조 성능/구조 실험**으로 취급한다.

# 29. 권장 논문 표현

> **Both the conventional baseline and the proposed configuration use the same M1 write-ingress queue, downstream ingress-index metadata, and AXI ordering infrastructure. Conventional entries allocate per-line coherence trackers in ingress age order, allowing snoop processing to be pipelined for multiple queued writes while downstream AW/W issue remains head-ordered. In the proposed configuration, range classification occurs when an AW is accepted into the common ingress queue, and range-classified writes bypass per-line tracker allocation. Consequently, the post-route resource difference reflects the incremental range mechanism rather than a mismatched queue or response-association structure.**

또한:

> **Runtime tracker usage is evaluated separately from static area. With equal ingress and tracker depths, the proposed mechanism reduces conventional per-line tracker occupancy for memcpy traffic, but this occupancy reduction alone is not interpreted as a throughput or latency improvement. A separate tracker-depth sensitivity experiment is used to evaluate whether the range path reduces memcpy backpressure when the number of conventional tracker entries is constrained.**

# Appendix D. 핵심 runtime 차이

### B1

```text
M1 memcpy AW
→ Common Ingress Queue
→ Conventional Tracker allocation
```

```text

```

> **동일한 transaction ingress를 유지하면서 memcpy coherence bookkeeping을 per-line tracker에서 page-bounded range state로 옮기는 것**

```text

LINE_TRACKER_ENTRIES = 16
```


sensitivity experiment에서 평가한다.
